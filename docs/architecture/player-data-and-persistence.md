# 玩家数据、资产与持久化设计

> 2026-09-25 实现进展：注册、登录与基础档案本地闭环已落地，参数、范围和验证见[首个实现里程碑](account-save-milestone.md)。下文仍为完整目标草稿；未实现部分不因本轮交付视为已批准或已完成。

设计状态：Draft。更新日期：2026-09-24。实现状态：基础闭环已部分实现与验证，完整目标尚未完成。

本次补充用户数据的归属、写入、恢复与活动生命周期设计；下述模型是候选逻辑结构，不是已确认的 SQL 表、正式接口或已经落地的数据库。数据库选型、保留期限和恢复目标仍待确认。

上级入口：[底层设计](foundation-design.md)。关联：[账号与会话](accounts-and-sessions.md)、[1.0 大纲](../versions/1.0/outline.md)、[运行维护](../operations/README.md)、[验收清单](../../tests/README.md)。

## 1. 数据的唯一正式来源

永久进度和资产由服务端确认并保存。客户端可以保存界面设置与展示缓存，但不能上传整份 PlayerData 覆盖正式存档，也不能自行提交捕捉成功、战斗胜利或应得奖励作为可信事实。

所有玩家相关操作通过有效会话取得操作者身份；目标 ID 只是查找参数。读取也要授权，不能只保护写入。活动插件通过常驻能力访问自己的业务数据，不持有任意 SQL 或生产存档访问权。

账号认证数据与游戏数据逻辑分开，仍可存放在同一数据库；不因此引入账号微服务、资产微服务或多个数据库。

## 2. 候选逻辑模型

| 对象 | 内容与标识 | 关键约束 |
| --- | --- | --- |
| Account / Session | 账号及会话，具体设计见账号正文 | 不向普通客户端、插件和日志公开凭据 |
| PlayerProfile | userId、昵称、初始化状态、全局进度 | 建议每账号一份；昵称不是资产归属键 |
| PetInstance | 实例 ID、所有者、宠物定义 ID、等级、经验、进化阶段 | 种类定义与玩家实例分开；定义不能随活动退场失效 |
| Inventory / Currency | 玩家、物品或货币 ID、持有数量 | 消耗不产生负数；数量类型、上限与可交易范围由规则限定 |
| Team | 玩家、位置与宠物实例引用 | 只能引用有权使用的宠物；队伍大小和重复上场规则待定 |
| ActivityProgress | 玩家、activityId、runId、schemaVersion、revision、专属进度 | 按活动与轮次隔离；插件不能读写其他活动内部状态 |
| BattleState | 战斗/遭遇 ID、参与者、状态、行动序号、内容版本、必要随机状态 | 支持重连；随机状态留在服务端；已结束战斗不能重新结算 |
| CommandReceipt / ClaimRecord | 操作者、操作类型、请求标识、参数摘要、结果；业务领取资格 | 请求重试去重与一次性奖励约束分开 |
| AssetChange / AdminAudit | 资产变化、原因、关联操作、必要管理记录 | 用于复现和纠错；不等于要实现事件溯源系统 |

这些是职责与数据关系，不要求一个对象一张表、一个类或一个独立模块。活动自己的有限结构化进度可存为经过校验的 JSON；账号、资产所有权和关键领取约束不能只藏在任意插件 JSON 里。

## 3. 必须区分的身份与版本

`userId` 标识玩家，`petDefinitionId` 标识宠物种类，`petInstanceId` 标识实际拥有的个体。资产关联稳定 ID，不使用昵称、显示名或可改动文件路径作为归属依据。

`activityId` 标识活动类型，`runId` 标识一次开放/复刻轮次，`contentVersion` 标识本次使用的规则与内容，`schemaVersion` 标识存储结构，`revision` 标识某份运行数据的并发版本，`requestId` 标识一次请求。这些含义不能混用。

活动临时停用再恢复，建议保留同一轮次；正式复刻是否建立新轮次、是否重新给予领取资格，由策划明确。不能仅换插件构建版本就让玩家重复领奖，也不能清空旧领取记录来模拟复刻。

战斗开始时绑定所需规则与内容版本。旧版本不可用或数据不兼容时，必须排空、迁移或按批准的终止策略处理；不能把旧快照静默交给新规则执行。

## 4. 统一写入边界

业务提交“操作意图”，常驻系统组织授权、校验、事务与结果保存。使用数据库事务并不自动解决业务遗漏：哪些状态应一起成功，需要逐项定义。SQLite 的事务提供数据库层的提交/回滚基础；实际业务边界仍由项目实现。[D1]

建议每次写入采用：

```text
解析并限制输入 → 验证会话与操作权
    → 开始短事务
        → 读取已有请求结果；相同请求参数不一致则拒绝
        → 重新校验对象归属、当前状态、业务领取资格和并发版本
        → 计算或应用被验证的服务端结果
        → 写入全部相关变化、结果与必要记录
    → 提交成功
    → 更新内存视图并发送结果
```

事务内不进行网络调用、播放动画、等待玩家输入或长时间密码计算。状态合法性检查不能全部放在事务外，否则两个请求可能基于同一旧状态分别成功。

正式成功响应必须在提交后发送。响应或推送失败不撤销已提交资产；客户端重新查询状态或原请求结果。进程内缓存不能先改变后假装数据库一定成功。

### 4.1 关键业务的原子范围

| 操作 | 必须整体一致的变化 |
| --- | --- |
| 注册 | 邀请消耗、账号、基础玩家档案；密码哈希计算在进入写事务前完成 |
| 初始资产领取 | 领取资格、初始宠物/道具、初始化完成标记和结果 |
| 捕捉 | 道具消耗、遭遇状态、随机结果、成功时的宠物实例和请求结果 |
| 领取/兑换 | 服务端确认的领取条件、业务领取记录、材料消耗、奖励与结果 |
| 升级/进化 | 资格与当前个体状态、消耗、等级/形态变化、必要队伍引用和结果 |
| 战斗行动/结算 | 行动序号、战斗快照、随机状态、相关持久消耗/奖励和结束标记 |

这里不预设具体倍率、进化材料、死亡损失或合作奖励分配。业务设计确认后补全细项；不能由 Agent 为通过测试擅自决定资产规则。

### 4.2 重复请求与并发

建议请求去重范围至少包括操作者、操作类型和请求标识，同时保存规范化参数摘要。相同请求重复到达返回已提交结果；相同标识带不同参数则拒绝，不覆盖原记录。

请求去重不是唯一的领奖约束。一次性领取还要有玩家、活动轮次与奖励资格的唯一性保护；换 requestId 或清理短期请求缓存后仍不能再领取同一资格。初始宠物使用永久的一次性业务记录，不跟随活动轮次重置。

并发策略应使用明确的事务/条件更新与版本检查。两个标签页争用最后一个道具时，只能有一次合法消耗；旧页面的有效登录态也不能绕过状态冲突。已经提交的原请求重试应优先查到自己的记录，而不是因其携带旧 revision 被误判后再次执行。

请求记录保留时间、客户端重试窗口、业务资格记录保留规则需要一起确定。过期或无法判定的旧请求要求重新同步，不承诺网络消息只投递一次，也不盲目重新抽取结果。

## 5. 存档、断线与随机结果

建议每次有效战斗指令结算后保存必要快照，而不是仅在关闭网页或点击保存时写入。展示动画、相机与粒子状态不属于权威存档。

提交前失败：不留下部分资产变化。提交后响应丢失：恢复原结果。服务端重启：加载已提交快照和结算记录；不能重新生成已经确认的奖励或捕捉结果。战斗超时、合作玩家离线等行为由玩法规则另行定义。

随机结果由服务端决定，必要状态与对应业务一起提交；客户端不提供正式随机种子或成功结果。固定种子只作为隔离测试能力，不暴露生产随机状态。对未提交操作如何产生随机值，应与重试/并发策略一并验证。

客户端收到会话过期时只清理登录状态与敏感缓存，不清空正式进度；重新登录后读取自己的数据。正常重启是否保留有效登录会话应由账号模块明确，但不影响玩家资产的持久性。

## 6. 活动进度与永久资产

火山节可以退场，玩家获得的焰狐仍属于永久资产。活动进度记录任务状态，不能成为焰狐个体的唯一存储位置；宠物定义、技能与必要素材也必须能在活动关闭后解析。

插件声明需要的进度结构、保留规则及升级方式，由宿主限定活动、轮次、玩家和操作范围。数据读写与奖励结算共用公共事务边界，避免插件先标记完成、发奖失败后永远无法重试。

停用时可以释放运行缓存、监听和临时资源，但不能自动删除领取记录、未结算义务或玩家永久资产。归档与删除是有独立条件的维护操作。旧活动重新开放或复刻时，按策划批准的轮次与奖励资格执行。

永久宠物规则升级可能需要单独的兼容或迁移方案，不能仅保留一个 ID 就声称存档兼容。账号停用、退出登录和活动停用也都不等于删除玩家数据。

## 7. 存储与迁移建议

建议从单进程服务与 SQLite 起步；本轮已用 Node.js 内置 SQLite 建立账号、邀请、会话、档案与回执表；其余资产模型未实现，也不同时维护 SQLite/PostgreSQL 双实现。

若选 SQLite，需明确外键、唯一性/非负约束、连接与写入策略、事务失败处理及备份配置。WAL 允许读写并行，但同时仍只有一个写入者，不应据此假设多请求可以无冲突写入。[D2]

正式数据库、备份、日志和服务端密钥位于受保护的持久化位置，独立于构建产物与公开静态目录。发布不能覆盖存档；测试、Playground 与生产使用独立数据和凭据。

数据结构迁移使用可追踪版本与旧存档样本验证；区分数据库结构版本、插件进度结构版本和内容版本。重要迁移前备份，失败时停止开放而不是自动新建空库继续提供服务。

代码回退只有在旧代码兼容当前数据时才可执行。破坏性迁移默认安排维护窗口并设计恢复步骤，不承诺任意版本都能无损回退。

## 8. 备份、恢复与数据最小化

使用能生成一致快照的方法并保存到独立位置；例如 SQLite 官方在线备份 API。[D3] WAL 模式运行时不能只随意复制主数据库文件并忽略配套状态。[D2]

恢复演练应验证账号、宠物、背包、领取记录、活动进度与相关内容能共同工作，不以“数据库文件存在”作为成功依据。恢复时记录备份时间、匹配代码/内容版本、受影响玩家及可能丢失的进度；恢复点目标与恢复时间目标待人类确认。

数据库回到旧时间点可能使会话、重置凭据、账号停用或密码变更记录倒退。恢复流程建议撤销全部会话和重置凭据，复核账号状态；必要时要求受影响账号重新核验/重置密码，不能仅清 Cookie 就声称安全恢复。

备份含认证和资产数据，应限制访问并采用合适的加密保护；密钥与备份分开管理。保留期限、删除申请及备份中的延迟清理策略需另行确定，不擅自清档。

日志只保留复现所需标识、操作、结果和必要变化；密码、完整会话、恢复凭据和不必要的个人信息不入日志。[D4] 默认给 Agent 合成/脱敏样本与有限错误记录，不提交生产数据库、备份或密钥到仓库。

## 9. 实施顺序与验收

先验证：注册 → 登录 → 创建基础档案 → 领取一次初始宠物 → 退出 → 重新登录 → 服务端重启 → 原数据仍可恢复。使用两个账号同时验证读取与修改隔离，之后再接入捕捉、成长与首个活动。

候选场景 D01–D10 与账号 A01–A10 见[验收清单](../../tests/README.md)。保留原 C01–C15，不用本次场景替换原有公共约束。完整清单尚未全部实现；基础档案的重试、冲突、回滚和恢复已有局部运行证据，见本轮里程碑。

实施前待确定：实际数据库和驱动、字段与约束、初始资产规则、并发/重试窗口、请求与业务记录保留期、多人会话语义、活动复刻轮次、迁移工具、备份频率、恢复目标和数据删除流程。

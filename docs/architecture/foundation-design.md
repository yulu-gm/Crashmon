# 常驻系统底层设计工作稿

设计状态：Draft。日期：2026-09-24。实现状态：未实现。本文是下一轮设计骨架，不是正式 API 或已冻结技术方案。

## 1. 已确认方向

常驻系统 + 活动插件，版本内容追求热插拔；小规模多人抓宠回合制；人类设计、Agent 编码与维护。

以下沿用[总体方案](../overview/design-v0.1.md)中的建议，具体细节仍待确认。常驻系统只服务 Crashmon，不建设通用游戏引擎。

## 2. 首条业务链

候选闭环：登录 → 组队 → 遭遇 → 战斗与捕捉 → 成长 → 保存与重新进入，再接入一个可开放、收尾、停用的完整活动。

多人形式和玩法含义以[核心玩法](../game-design/core-rules.md)与[1.0 大纲](../versions/1.0/outline.md)的确认结果为准，不默认独立冒险或同场合作。

## 3. 候选公共职责

| 职责 | 负责 | 不负责 |
| --- | --- | --- |
| 玩家与资产 | 归属、持有、消耗、发放、保存 | 为活动绕过公共资产结算 |
| 战斗与成长 | 行动、效果、状态、升级、进化 | 在主流程增加具体宠物身份特判 |
| 活动宿主 | 接入、开放、会话归属、收尾、清理 | 各活动的专属任务流程 |
| 内容装配 | 引用校验、内容版本、必要依赖 | 把活动退场等同于删除永久宠物 |
| 客户端表现 | 输入、界面、场景、动画 | 正式伤害、胜负与奖励裁决 |

职责不要求一一对应类、软件包或服务。

## 4. 依赖与公开能力：待细化

建议内容只依赖公开能力，app 装配公共系统与具体内容。活动不导入其他活动内部实现，框架不主动导入具体活动。

针对首个活动列出最小能力。逐项说明调用方、授权范围、可信输入、输出、失败、重试与持久变化，不提供能访问全部服务的万能上下文。

允许具体技能和活动使用清晰业务代码，不强求全部配表。永久宠物需要的规则与素材必须独立于可退场活动。

## 5. 数据与命令：待设计

区分玩家 ID、宠物种类 ID、宠物实例 ID、活动 ID、活动轮次、内容版本与请求标识。

设计捕捉、领取、兑换、升级、进化的事务与重复请求行为；区分未提交、已提交但响应丢失、过期请求。客户端不得自行报告最终获宠结果。

明确断线和重启后恢复的状态、随机状态与去重记录，以及并发冲突如何处理。数据库结构与访问接口尚未确定。

## 6. 生命周期与版本：待设计

候选流程：加载并校验 → 已加载未开放 → 开放 → 收尾 → 停用。

覆盖加载失败清理、重复启停、拒绝新会话、已有会话结算和强制终止的资产策略。只隐藏页面不等于服务端关闭。

在线启停、内容切换、任意代码不停服替换分别验收。若要旧会话继续运行，需要保留其代码、素材与兼容数据；无法安全共存时明确维护和排空策略。

模块边界不等于运行时安全沙箱，不默认允许未经审核上传脚本。

## 7. Playground 与验证：待设计

运行同一正式规则与独立测试数据，提供组队、阶段跳转、固定随机场景、重置和启停测试。不得访问生产密钥或修改正式资产。

验证位置：[tests/](../../tests/README.md)。总体方案 C01–C15 是候选公共验收基线，后续落实成真实测试；文档存在不代表通过。

## 8. 技术选择：待确认

总体方案建议 TypeScript、2D、模块化单体与轻量存储。根据多人形式和表现需求冻结技术栈与版本，当前不安装依赖或构造虚假的运行接口。

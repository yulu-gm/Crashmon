## 1. 目标与边界

玩家能够建立自己的身份、登录并恢复进度；换浏览器、会话过期和活动退场不改变永久资产归属。账号恢复必须有受控流程，不能依赖 Agent 临时修改生产数据库。

认证回答“你是谁”；会话将后续请求关联到已认证身份；授权检查该身份能否执行当前操作。登录成功不能代替对象归属和操作权限检查。[S1][S4]

这些是单个后端内部的职责，不要求独立账号服务器、身份平台或额外数据库。活动插件不实现自己的账号体系。

## 2. 首版候选方案

建议采用邀请制注册、账号密码登录、服务端会话。一个账号对应一个玩家档案；暂不建设多角色、多区服、短信登录或多个社交账号绑定。具体认证库在技术栈确认后选定，优先使用成熟实现，不自研密码算法或认证协议。

| 能力 | 建议行为 |
| --- | --- |
| 注册 | 使用有效邀请凭据，由玩家设置登录名与密码 |
| 登录 | 验证凭据与账号状态，创建新会话，返回可公开的自身信息 |
| 首次进入 | 恢复或初始化玩家档案，通过统一结算领取一次初始宠物 |
| 恢复登录状态 | 验证服务端会话后读取自身数据；不信任浏览器的“已登录”标记 |
| 退出 | 撤销服务端当前会话并清理 Cookie；与删除存档无关 |
| 修改密码 | 重新验证身份，更新密码；建议撤销全部旧会话后重新登录 |
| 找回账号 | 通过已确认的核验渠道签发短期、一次性重置凭据 |
| 停用账号 | 拒绝后续访问并撤销会话；不默认删除资产 |

以上是功能语义，不是已冻结的 URL、接口签名或数据库表结构。

## 3. 身份与数据关系

`userId` 是服务端生成的稳定内部身份；登录名是登录标识，昵称是展示字段。修改昵称或密码不改变 `userId` 和资产归属。客户端不能在请求中选择自己要扮演的 `userId`。

建议账号记录包含稳定身份、规范化登录名、密码哈希及其算法参数、账号状态和必要时间；会话记录包含会话凭据摘要、所属账号、创建与过期时间、撤销状态。使用经过设计的随机凭据及安全存储方式，不在公开响应或普通日志中暴露完整凭据。[S2]

登录名大小写、Unicode 规范化、长度和改名策略需要在建立唯一约束前明确。昵称的长度与展示规则单独定义；不因为昵称相同而合并账号。

账号、玩家档案和资产在逻辑上分开。账号可以已创建但尚未完成初始宠物选择；此时重新进入恢复初始化流程，而不是重新创建账号。游戏数据细节只维护在[玩家数据正文](player-data-and-persistence.md)，这里不复制表结构。

## 4. 注册、登录与初始化流程

### 4.1 注册

服务端校验输入与邀请资格，再在一个受控操作中消耗邀请、创建账号和基础玩家档案。建议邀请一次使用、可过期、可撤销；并发请求必须受数据库唯一性或条件更新保护，不能让一份邀请创建多个账号。

密码哈希计算应有资源限制，且不在持有数据库写锁期间执行。校验与真正提交之间仍需在事务中重新检查邀请和登录名约束，不能只在事务外检查一次。

注册成功但响应丢失后，玩家应能通过登录恢复已有账号；不得为了“重试方便”绕过邀请约束或创建第二份资产。邀请创建与撤销属于受控管理操作，活动作者没有该权限。

### 4.2 登录与恢复

```text
提交凭据 → 服务端认证与账号状态检查 → 创建新会话
    → 浏览器接收会话 Cookie → 请求自己的公开玩家状态
    → 未初始化则继续初始化；已初始化则恢复已有进度
```

登录失败、账号不存在和恢复申请应采用不易枚举账号的对外响应，并对尝试次数进行限制；详细原因进入受保护的内部记录。[S1]

建议多设备持有独立会话，但不允许各设备覆盖整份存档。退出当前设备与退出全部设备分别定义；是否限制同账号并行游戏会话尚待确认。

### 4.3 初始资产

“账号首次创建”和“领取初始宠物”是两个有不同重试语义的操作。建议用持久的一次性初始化/领取记录保护初始资产，宠物实例、必要初始道具与初始化完成标记整体提交。

不能仅依赖前端第一次展示页面，也不能每次登录重新执行发宠逻辑。初始宠物是否由玩家选择、可选范围和是否允许重新选择由玩法设计决定。

## 5. 会话与每次请求的权限

建议同源提供网页与游戏接口，减少不必要的跨域配置。正式环境全程 HTTPS，会话通过 `HttpOnly`、`Secure` 和适当 `SameSite` 策略的 Cookie 传递；建议从 `SameSite=Lax` 评估，不设置过宽 Domain。浏览器不在 localStorage 保存登录令牌。[S2]

Cookie 设置不能代替完整的安全设计。修改状态的接口要使用成熟的 CSRF 防护并校验可信来源，不能用 GET 执行发奖、退出或修改密码；也不能把 CORS 当作身份验证。[S3]

每次受保护操作执行：有效会话 → 账号仍可用 → 操作权限 → 对象/会话归属 → 当前业务条件。目标宠物 ID、战斗 ID 或活动 ID 只是定位参数，不能赋予访问权。[S4]

登录或权限提升时更新会话标识，避免沿用不可信会话。由服务端判断闲置超时、绝对有效期和撤销；数值在上线前确认。退出只撤销指定会话，修改密码、恢复账号和停用账号建议撤销所有旧会话。[S2]

若后续采用 WebSocket，需要验证握手身份与 Origin，并在会话过期、撤销或账号停用后终止相关连接或拒绝后续操作；不能只在建立连接时验证一次。具体通知方式随通信方案设计。

会话失效后，客户端停止新的资产操作并提示重新登录。服务端已提交的结算不回滚；重新认证后查询原结果或恢复快照。角色是否自动行动、战斗是否暂停或超时结算属于待确认的玩法策略，不能由登录模块自行决定。

## 6. 密码、恢复与管理权限

### 6.1 密码保护

使用成熟密码哈希库，建议 Argon2id，保留盐和算法参数；不保存明文或可逆加密密码，不用普通 MD5/SHA-256 代替密码哈希。参数需依据当前安全建议与目标机器基准测试选择，升级时设计渐进重哈希，不把本文当成已冻结参数表。[S5]

支持长口令及密码管理器，不静默截断。口令长度、常见泄露口令拒绝规则、请求大小、失败次数和密码哈希并发限制均需在实现前明确。小规模玩家不代表公网接口可以不限制滥用。

### 6.2 账号恢复

首版可考虑管理员通过预先建立的可靠联系渠道核验，再签发一次性重置凭据。渠道、身份核验标准、负责人与无法核验时的处理规则必须在人类确认后写入运行手册；不能仅凭昵称、公开战绩或聊天自称重置账号。

重置凭据需随机、限时、单次有效并安全保存。重置成功时更新密码、消费凭据并撤销旧会话；并发使用只能成功一次。旧密码不可查询或发送。申请重置本身不能让陌生人锁住目标账号。[S6]

不擅自增加手机号、真实姓名或未确认用途的邮箱收集。没有邮件服务时，不虚构邮件找回能力。管理员不应直接设置并知晓玩家长期密码。

### 6.3 管理与内容权限

首版只定义普通玩家与必要的受控管理能力，不先建设复杂权限平台。活动作者、Agent、游戏管理员和仓库维护者不是自动等价身份；具体管理能力需独立授权。

停用、恢复、补偿和账号恢复操作需要重新验证管理身份及审计。生产管理员的强认证方式、首个管理员如何安全建立、紧急恢复如何授权，作为上线前待决项；不得使用默认密码或让普通注册选择管理员角色。

## 7. 插件、客户端与日志边界

插件只获得与当前业务有关的玩家身份、进度和结算能力，不读取账号凭据、会话存储或任意玩家数据库。权限必须在常驻系统执行，目录结构和提示词不构成安全隔离。

客户端共享类型使用公开视图，不直接序列化账号实体。响应中不包含密码哈希、恢复凭据、其他设备会话或服务端秘密；退出/切换账号时清理前一账号的客户端缓存，个性化响应不能进入公共缓存。

记录认证失败、会话撤销与管理操作的必要信息，关联可供排查的请求编号。普通日志不记录密码、完整 Cookie、会话或重置令牌；不将这些数据交给 Agent 调试。[S7]

## 8. 验收与待决项

候选场景 A01–A10 见[公共验收清单](../../tests/README.md)。完整清单仍是目标规范；基础注册、登录与会话已有局部运行测试，尚无完整安全审计通过结论。

实施前需要确认：登录方式与邀请规则；登录名规范；口令策略与库；会话/邀请/重置有效期；多设备策略；限流参数；账号恢复核验渠道；管理员建立与认证方式；账号删除和安全记录保留策略。

无论最终采用密码登录还是外部身份服务，服务端身份绑定、对象授权、可撤销访问和永久资产归属仍需由 Crashmon 验证。

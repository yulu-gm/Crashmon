# Crashmon 1.0 内容大纲

设计状态：Draft。更新日期：2026-09-24。实现状态：未开始。尚无冻结内容清单、发布日期或上线承诺。

## 1. 本版目标

建议验证：账号和永久数据可靠；基础抓宠和队伍战斗构成完整循环；一个活动可以独立接入与退场；新设计者和 Agent 能依据仓库继续制作内容。

1.0 覆盖哪些共创和运营演练需要确认。长期留档仍必须满足总体方案的数据、发布与恢复门槛；不能先让玩家积累永久资产，再补身份隔离、事务和恢复能力。

## 2. 玩家体验

待确定多人形式、一次游玩目标、设备、二维或三维表现。进入方式建议邀请制账号密码登录，尚未确认；基础流程见[账号设计](../../architecture/accounts-and-sessions.md)。

多人形式影响第一条完整流程，不能将多个账号独立登录直接视为完成合作玩法。账号有效性、会话失效与游戏内断线行为分别设计，不能让登录模块自行决定战斗暂停或奖励损失。

## 3. 首条可玩流程：候选

先完成基础闭环：获得进入资格 → 注册 → 登录 → 创建玩家档案 → 领取一次初始宠物 → 退出并重新登录 → 恢复同一份资产。两个账号相互隔离，服务端重启后仍可恢复。

再扩展：组队 → 基础区域 → 遭遇 → 战斗与捕捉 → 成长 → 保存并重新进入。

接入一个包含进入、推进、挑战、获宠与退场的活动。若确认合作同场为核心，应在该流程中验证。

初始宠物是否可选、可选名单和重复选择规则待策划确定；不能为了演示随意永久发放示例宠物。

## 5. 反推底层需求

实际内容逐项列出需要的公共能力、缺口和验收，回填[底层工作稿](../../architecture/foundation-design.md)。当前没有已经实现的公共能力。

需要公共机制扩展的宠物或活动必须明确提出需求，不夹带框架重构或绕过资产结算。活动作者可以设计获宠条件，正式身份、归属、消耗与发奖由常驻系统保护。

## 6. 范围限制：待确认

原稿建议先不做实时开放世界、复杂交易、公会、任意脚本上传、复杂繁育、海量装备和完整 PvP 平衡。这些是候选范围控制，不是永久禁止。

账号侧建议先不做多角色、多区服、短信登录和多种外部账号绑定；不能因此省略账号恢复、权限检查或密码保护。邀请、会话、管理员、备份及保留参数仍需确认。

需要明确首版热插拔是在线启停、内容切换，还是还包括代码无重启替换。

## 7. 验收与开放

验收入口：[公共场景](../../../tests/README.md)。保留 C01–C15，新增 A01–A10 与 D01–D10。这里只引用范围，不重复维护完整安全与数据规范。

首次长期留档前，至少提供以下真实证据：

- 注册与登录可用；退出、过期、恢复与账号停用后的访问按规则失效；账号之间不可越权读写。
- 初始宠物只领取一次；重复请求、并发和结算故障不制造或丢失部分资产。
- 退出重进、响应丢失与服务端重启能恢复已确认状态；旧存档有兼容验证。
- 活动启停收尾与永久宠物保留经过验证；测试能力不接触生产数据。
- 实际发布、迁移、备份恢复与账号恢复已演练，权限与责任人明确。
- 完整流程可试玩，选定的多人模式有相应验证，而不是只验证多个账号。

每项登记具体场景和证据，未执行保持未验证；文档和目录存在不等于功能完成。

## 8. 下一轮设计顺序

并行确认登录方式与初始资产流程、多人形式与最小战斗规则。先建立账号和存档闭环，再用候选宠物组合及一个活动检验公共能力，不要求一次决定全部远期玩法。

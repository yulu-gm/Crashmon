# Crashmon 1.0 内容大纲

设计状态：Draft。更新日期：2026-10-06。实现状态：账号、基础档案、多人二维据点和初始领宠已实现，另有角色与场景美术样本；B0 本地 PvE 与五只伙伴已接通，通过遭遇卡片开战；完整野外、升级进化与完整首章尚未实现，未部署。尚无冻结内容清单、发布日期或上线承诺。

## 1. 本版目标

建议验证：账号和永久数据可靠；基础抓宠和队伍战斗构成完整循环；一个活动可以独立接入与退场；新设计者和 Agent 能依据仓库继续制作内容。

1.0 覆盖哪些共创和运营演练需要确认。长期留档仍必须满足总体方案的数据、发布与恢复门槛；不能先让玩家积累永久资产，再补身份隔离、事务和恢复能力。

## 2. 玩家体验

已确认方向：玩家操控主角进入地图，并在 NPC 处领取初始 Crashmon。后续已开始明确宇宙探索与幽默伙伴的题材，以及细线、柔和色块的复古幻想场景方向；美术规范与用户参考图见[美术方向 v1](../../game-design/art-direction-v1.md)。完整流程只维护在[首次体验工作稿](../../game-design/first-session.md)，本文件引用范围，不复制具体技能、台词或教学规则。

原型目标是让玩家选择伙伴、亲手捕捉第二只、体验同时上场的配合，并知道下次出发想做什么。已有功能命名与占位素材保留到新表现通过验证；首章怎样串起星球、生态、笑点与挑战见[内容提案](universe-content-proposal.md)，具体名称和种族不自动定案；约 20–30 分钟是首次试玩节奏目标，不是已验证时长、倒计时或整版内容长度。

2026-10-06 已确认准备队伍最多四只，由速度驱动行动。详细的[多单位战斗策划案 v0.1 / B0](../../game-design/battle-system.md)定义完整原型规则；双宠教学后可以逐渐增加到四只，不给主角另加第五个战斗位置。

据点已采用二维俯视、电脑优先并兼容窄屏点击；共享据点已实现，账号当前原型采用邀请制登录，长期参数见[账号设计](../../architecture/accounts-and-sessions.md)与实现记录。B0 先做一名玩家指挥小队的 PvE，合作战斗仍待专题设计，不以独立登录代替多人玩法验收。

账号有效性、会话失效与游戏内断线分别设计；B0 的战斗恢复和放弃语义见战斗正文，不能由登录模块临时决定奖励损失。

## 3. 玩家旅程与工程验证

### 3.1 首次玩家旅程

登录后进入据点并自由移动 → 与引导 NPC 交互、选择初始伙伴 → 进入小型野外区域、自主选择目标 → 首次战斗与捕捉 → 第二只加入队伍 → 双宠协作 → 区域挑战 → 成长与后续目标。

首次进化争取在首个完整区域章节内可体验，不强制挤进最初 20–30 分钟。NPC 三选一及确认后不重领已实现；两种教学捕获对象已有 B0-C1 定义与实现，正式成长和平衡待细化。行动成本、捕捉保护及失败处理以战斗 B0 为原型基线，不自动给正式玩家生成永久配置。

据点、领宠和基础入门流程长期可用；活动插件接在其上提供新体验，关闭活动不能阻断新玩家开始冒险。若确定同场合作是核心，也需在 1.0 完整流程中单独验证。

### 3.2 工程闭环与验收顺序

先验证注册、登录、玩家档案、一次性初始领取、退出重登、双账号隔离和服务端重启恢复，再接入战斗与活动。这是实现和验收顺序，不是让玩家主动退出、刷新和重启的新手任务。

战斗按 F01 单宠开局、F02 双宠资源与标记、F03 四单位与首领推进；覆盖四对四，并连接 B01–B30。先使用隔离测试数据验证规则，再接入真实身份、资产事务和新手流程。

随后验证首次体验全流程与一个可开放、收尾、停用的活动。已有资产安全与发布恢复要求不因先做占位原型而降低；测试内容不擅自发到正式账号。

## 5. 反推底层需求

实际内容逐项列出需要的公共能力、缺口和验收，回填[底层工作稿](../../architecture/foundation-design.md)。当前已实现账号、会话、基础档案、初始领宠与共享据点；B0 战斗与资产事务已接通；完整活动生命周期尚未实现。

B0 已实现独立于绘制的时间轴与效果结算、可恢复阶段、唯一行动、捕获和奖励事务及规则版本绑定，见[战斗框架](../../architecture/battle-framework.md)。普通与首领胜利按配置补 1 基础球，教学不发；补给和奖励仅为本地原型经济。

需要公共机制扩展的宠物或活动必须明确提出需求，不夹带框架重构或绕过资产结算。活动作者可以设计获宠条件，正式身份、归属、消耗与发奖由常驻系统保护。

## 6. 范围限制：待确认

题材与美术按真实游玩构图、角色一致性和关键交互逐步验证，不因战斗设计重新绘制全地图或迁移引擎。主角跟宠和精细剧情不是战斗规则验证的前置条件；B0 主角没有独立战斗槽位、技能或养成。

B0 不支持战中替补、第五单位、召唤、复活、行动外终结技和复杂触发链；不上线未经验证的正式奖励。数值与费用明确用于原型，完整成长和经济仍需内容设计。

原稿建议先不做实时开放世界、复杂交易、公会、任意脚本上传、复杂繁育、海量装备和完整 PvP 平衡。这些是候选范围控制，不是永久禁止。

账号侧建议先不做多角色、多区服、短信登录和多种外部账号绑定；不能因此省略账号恢复、权限检查或密码保护。邀请、会话、管理员、备份及保留参数仍需确认。

需要明确首版热插拔是在线启停、内容切换，还是还包括代码无重启替换。战斗中的规则版本不随活动启停悄悄改变。

## 7. 验收与开放

验收入口：[公共场景](../../../tests/README.md)。保留 C01–C15、A01–A10 与 D01–D10；首次体验 E01–E12 维护在[体验正文](../../game-design/first-session.md)；新增 B01–B30 只维护在[战斗正文](../../game-design/battle-system.md)。自动化验证状态，人类试玩验证理解、选择与节奏，二者不能互相替代。

首次长期留档前，至少提供以下真实证据：

- 注册与登录可用；退出、过期、恢复与账号停用后的访问按规则失效；账号之间不可越权读写。
- 初始宠物只领取一次；重复请求、并发和结算故障不制造或丢失部分资产。
- 退出重进、响应丢失与服务端重启能恢复已确认状态；旧存档有兼容验证。
- 战斗行动顺序、状态寿命、成本、捕捉和终局可复核；断线不重复跳伤、随机或发奖。
- 活动启停收尾与永久宠物保留经过验证；测试能力不接触生产数据。
- 实际发布、迁移、备份恢复与账号恢复已演练，权限与责任人明确。
- 完整流程可试玩，选定的多人模式有相应验证，而不是只验证多个账号。

每项登记具体场景和证据，未执行保持未验证；文档和目录存在不等于功能完成。B0 的战后满血、捕获保留、24 小时不活跃放弃及正式掉落权益在开放前需确认。

## 8. 下一轮设计顺序

2026-10-06 后续安排：用户要求初版 P0 参考早期赛尔号的完整系统，明确下一步为物品与背包、基础经济与商店、精灵养成，并要求先制定计划、归档 Markdown。下一阶段执行顺序以 [P0 专题计划](p0-items-economy-growth-plan.md)为入口，先完成规则与数据设计，再实施资产底层、界面和成长。完整野外继续保留在 1.0 范围中，不作为这轮系统闭环的前置条件；具体数值、进化形态数量和培养细则仍待定案。以下较早安排保留背景，优先级以本段为准。

2026-10-06 已实施首版战斗框架与五只伙伴，主 Agent 完成独立自动化及浏览器验收，具体范围见[本轮记录](../../verification/battle-2026-10-06.md)。后续优先人类试玩和平衡，再设计完整野外、升级进化与区域挑战。此前 2026-09-25 “暂缓战斗、先完成账号”的安排保留为历史背景，不再是当前限制。

动作样本继续为表现提供输入，但不决定战斗技能、等级或数值。具体宠物正文进入 docs/content/pets/，通用规则维护在战斗策划案；再设计首次进化、遭遇奖励和完整区域挑战。

同时保留登录方式、多人形式和数据安全的确认与工程闭环。以具体流程反推底层能力，不先建万能框架，也不要求一次决定全部远期玩法。

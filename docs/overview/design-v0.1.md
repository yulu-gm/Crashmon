# 共创抓宠回合制页游
## 总体设计与持续运营维护方案

**版本：v0.1 · 讨论整理稿**  
**日期：2026-09-24**  
**核心结构：常驻系统 + 活动插件**  
**协作方式：人类负责设计与产品决策，Agent 负责实现与技术维护**

> 本文整合本次讨论，作为后续设计、Agent 实现和验收的共同基线。它不是已实现系统的说明，也不代表服务器容量、热更新能力或恢复能力已经通过验证。文中明确区分已确认方向、首版建议与待定事项；尚未确认的建议不得被 Agent 自动当作最终产品要求。

---

## 01｜项目定位与设计结论

### 1.1 项目概述

制作一个面向小规模熟人社区的多人在线抓宠回合制页游。预计总玩家约 10–20 人，同时在线约 5–10 人。玩法参考《赛尔号》的宠物获取与养成，以及《崩坏：星穹铁道》的队伍回合制战斗体验，但不直接照搬两者完整系统。

玩家拥有多只宠物，选择一支队伍参与战斗。每只宠物的技能数量较少，可通过升级和进化成长。版本持续推出新宠物及活动，玩家通过捕捉、挑战或活动奖励获得内容。

项目区别于普通小型网游的核心，是设计者可以按版本轮换。游戏应让新的设计者与 Agent 在清晰边界内完成创作，而不必重读整个项目或重写基础规则。

### 1.2 已确认的方向

| 事项 | 已确认内容 |
| --- | --- |
| 玩家规模 | 总玩家约 10–20 人，同时在线约 5–10 人 |
| 基本玩法 | 抓宠、队伍回合制战斗、少量技能、升级与进化 |
| 内容供给 | 按版本推出宠物与活动，通过捕捉或活动获得 |
| 共创模式 | 不同版本可以由不同设计者负责内容 |
| 顶层架构 | 常驻系统 + 活动插件 |
| 内容管理目标 | 版本内容可独立装配、启停与替换，追求热插拔 |
| 协作前提 | 人类不参与编码，只参与设计；编码与技术维护由 Agent 承担 |
| 长期要求 | 框架稳定、容易扩展、创作范围明确、可持续运营与维护 |

### 1.3 首版建议与尚待确认的事项

首版建议采用 2D 表现、全 TypeScript、模块化单体服务、服务端权威结算与 SQLite。建议先实现活动在线启停，再单独评估任意代码不停服热替换。这些是方案建议，不是用户已经逐项确认的技术选择。

多人模式、队伍人数、行动顺序、完整数值体系、地图表现、移动端优先级、活动周期和故障恢复目标仍待确认。不得仅凭“同时在线”就推断必须存在实时共同地图、多人同场战斗或 PvP。

### 1.4 总体原则

**常驻系统保证游戏持续成立；活动插件持续提供新体验。内容可以独立退场，但不能带走玩家已经获得的资产，也不能留下无法收尾的运行状态。**

不建设通用游戏引擎，不提前建设 MMO 基础设施，不以“支持无限玩法”为第一阶段目标。新增结构必须对应当前明确需求；复杂度优先投入到规则边界、永久资产、可验证发布和故障恢复。

## 02｜玩法框架与首版范围

### 2.1 常驻游玩循环

```text
登录 → 查看宠物与队伍 → 进入区域 → 遭遇与战斗
     → 捕捉 / 获得奖励 → 升级与进化 → 调整队伍 → 再次挑战
```

常驻系统必须保留不依赖当期活动的基本游玩循环。即使一段时间没有新版本，玩家仍能进行基础战斗、养成和收集。

活动在此基础上提供新的获得途径、挑战组合、地图交互、故事和阶段目标，不应成为账号、背包和已有宠物正常工作的必要条件。

### 2.2 首版内容范围建议

| 维度 | 首版建议 | 说明 |
| --- | --- | --- |
| 队伍 | 3 只宠物同时上场 | 仅为讨论起点，实际人数待确认 |
| 单宠技能 | 2–3 个主动技能，最多 1 个被动 | 限制认知负担与触发复杂度 |
| 初始内容 | 6–8 只可用宠物、1 个基础区域、1 个完整活动 | 优先验证完整流程，而非数量 |
| 成长 | 等级、有限进化阶段 | 进化是否保留等级、消耗何物需设计确认 |
| 战斗效果 | 伤害、治疗、护盾、施加与移除状态、受限属性修改 | 按首批实际内容实现，不先补全万能效果库 |
| 活动形式 | 遭遇捕捉、挑战、累计目标、奖励兑换 | 允许受约束的流程代码，不强求全配表 |
| 美术表现 | 统一规格的 2D 宠物素材与可复用表现模板 | 不默认每只宠物都有完整独立动画管线 |

首版暂不纳入实时开放世界、复杂交易市场、大规模公会、无限脚本上传、复杂繁育、海量装备词条和完整 PvP 平衡体系。它们是范围控制，不是未来永久禁止。

### 2.3 多人模式必须先作产品决策

可选方向包括：各自冒险并共享社交与展示；多人进入同一场回合制战斗；共同地图上的实时活动；玩家对战。不同方向会改变房间管理、通信、断线规则与验收场景。

在未确认前，实施可以先验证多账号独立冒险、统一存档与并发结算，但不得声称已经覆盖完整多人合作。若多人同场战斗是核心乐趣，必须纳入第一条可玩的端到端流程，而不是最后再补。

### 2.4 战斗设计的公共约定

第一轮规则设计需要确认行动顺序、资源消耗、伤害与状态处理顺序、死亡判定、胜负与撤退、捕捉时机，以及被动、追击、反击是否允许互相触发。

每次行动应有明确的触发预算或终止规则，避免一个“技能数量很少”的宠物产生无限复杂的事件链。具体数值、元素克制与战斗公式不在本稿中凭空定案。

## 03｜总体架构：常驻系统 + 活动插件

### 3.1 两个大维度，不拆成多套独立服务

采用单仓库、模块化单体的首版架构。两大维度是职责与依赖边界，不代表两个仓库、两个服务器或两套数据库。

```text
浏览器：场景与动画 + 菜单与面板
                    │ 指令 / 状态 / 表现事件
                    ▼
应用入口：装配当前版本内容
    ├─ 常驻系统：规则、资产、存档、插件宿主、运营能力
    └─ 活动插件：活动流程、遭遇、挑战、页面、专属交互
                    │
                    ▼
             统一的数据存储
```

常驻系统是“这个游戏的基础框架”，可以直接理解宠物、捕捉、进化、战斗和活动，不需要抽象成通用 Entity/Component 平台。

### 3.2 职责划分

| 领域 | 常驻系统 | 活动插件与具体内容 |
| --- | --- | --- |
| 宠物与养成 | 宠物实例、持有关系、升级与进化操作、公共保存规则 | 具体宠物的属性、成长、技能、进化定义 |
| 战斗 | 行动流程、效果结算、状态生命周期、死亡与胜负处理 | 具体技能组合、活动敌人、挑战规则的受限扩展 |
| 遭遇与捕捉 | 创建遭遇、验证请求、消耗与发放、捕捉结果保存 | 出现地点、解锁条件、遭遇表、获得流程 |
| 活动与奖励 | 进度接口、领取记录、事务、重复请求保护 | 活动流程、任务条件、奖励配置、兑换规则 |
| 界面与表现 | 通用面板、表现事件、资源加载、输入边界 | 活动页面、专属素材和交互 |
| 插件管理 | 兼容校验、启停、会话归属、注册清理 | 声明依赖、注册功能、实现收尾策略 |
| 运维 | 日志、备份、权限、发布、维护入口 | 提供诊断信息与活动专属验收场景 |

具体宠物即使长期保留，仍然是具体内容；不因为生命周期长，就把每只宠物的实现写入常驻系统的公共流程。

### 3.3 依赖规则

内容模块只能使用常驻系统公开接口，不导入内部实现。活动不得直接导入其他活动的内部代码。真正需要共享的稳定能力，经单独评估后放入公开能力或公共内容定义，而不是让活动互相绑死。

应用入口负责选择和注册内容。常驻系统可以通过约定接口调用内容回调，但源码不应主动导入“火山节”或“焰狐”这样的具体实现。

允许存在当前业务所需的直接代码，不要求每个功能复制完整分层、增加接口工厂或注册中心。初版使用显式内容清单即可，不先建设动态插件市场。

### 3.4 建议目录

```text
app/                         客户端、服务端入口与内容装配
framework/                   常驻系统
  battle/                    公共战斗规则
  progression/               宠物、背包与成长
  activities/                活动公共能力与宿主
  public-api/                内容可使用的公开接口
content/
  pets/                      需要长期保留的具体宠物内容
  activities/                可独立启停的活动插件
playground/                  测试入口、场景与测试数据
tests/                       公共验收、兼容性与端到端测试
docs/                        设计、接口与运营规则
```

目录是逻辑组织建议，不是要求为每一项建立独立软件包。一个活动可以同时包含服务端规则与客户端页面；常驻系统不等于后端，内容层也不等于前端。

## 04｜常驻系统的核心能力

### 4.1 服务端权威结算

客户端提交“想做什么”，不提交需要被直接采信的结果。例如提交使用技能、消耗捕捉道具或领取奖励的请求，而不是提交最终伤害、捕捉成功或增加宠物。

服务端验证账号、对象归属、活动状态、行动权限、消耗、目标和当前状态版本，完成规则计算与持久化，再返回确认结果。浏览器负责表现和输入，不能成为永久资产的裁判。

### 4.2 规则与表现分离

```text
战斗状态 + 合法指令 + 内容版本 + 可控随机状态
                          ↓
                      战斗规则
                          ↓
              新战斗状态 + 结算事件
                          ↓
               客户端播放动作与界面
```

战斗核心不依赖 Phaser 场景、React 组件或浏览器时间。表现层可以播放动画、飘字与音效，但不自行修改真实血量和正式结果。

若客户端运行同一规则做预览，预览也不具有服务端结算权威。React 与 Phaser 读取同一份客户端状态视图，不各自维护互相矛盾的背包和血量。

### 4.3 原子操作、重复请求与并发

捕捉、领取、兑换、升级和进化等操作，需要具有明确的事务边界。一次捕捉应把消耗道具、记录结果、生成宠物和更新遭遇状态作为一致的业务操作，不能只完成其中一半。

每个可重试命令具有稳定请求标识或等价的业务唯一约束。重复请求应返回已处理结果，不再次执行；进程重启后也不能丢失关键去重记录。

同一玩家、宠物或战斗的冲突操作需要统一排序或状态版本校验。两个浏览器标签页同时消耗最后一份道具，最多一个成功；旧状态上的行动应被拒绝并要求同步，而不是覆盖新状态。

### 4.4 存档边界

建议持久化玩家、宠物实例、背包、活动进度、奖励领取、战斗快照、插件开放状态和必要资产变动记录。它们是业务记录，不要求采用完整事件溯源架构。

宠物种类 ID、玩家宠物实例 ID、活动 ID、活动轮次与内容版本必须区分。稳定 ID 不随文件改名而改变，不复用已经发布过的 ID 表达不同内容。

活动专属进度按活动命名空间存取，可使用带版本的结构化数据；插件通过公开接口访问，不自行连接生产数据库或修改公共数据表。

### 4.5 断线、重启与可复现性

每次确认的战斗行动保存必要状态，包括随机状态、行动序号及内容版本。恢复以服务器已确认结果为准，不能通过重连重新抽取捕捉或战斗结果。

用于复现的问题记录至少包含战斗或活动会话 ID、插件版本、规则版本、必要输入与随机种子或随机状态。实现应尽量做到同版本、同输入、同随机状态得到同样的规则结果；时钟等外部输入需明确注入或记录。

无需把所有调试细节永久保存。日志应有保留周期、大小上限和敏感信息处理规则。

## 05｜活动插件契约与创作边界

### 5.1 插件交付物

每个活动应交付身份与版本信息、公开 API 兼容要求、内容依赖、服务端规则、客户端入口与素材、活动进度结构、开放与收尾规则，以及对应测试。

插件元信息优先保持简单：插件 ID、版本、所需框架 API、依赖内容、入口、能力需求和活动数据版本。只有发生真实需求时再扩展，不设计通用插件协议大全。

“版本”是一份内容组合和开放配置，可以包含多个活动与永久内容更新，不必把每个版本做成一个不可拆分的大插件。

### 5.2 内容可以写代码，但不能取得全部权限

属性、倍率、奖励和素材引用优先用数据表达。独特技能与活动流程允许使用受审核的业务代码，不要求全部变成 JSON、节点图或自制脚本语言。

例如，焰狐技能可以判断目标是否灼烧，然后请求追加伤害或施加灼烧。公共框架负责伤害公式、护盾、死亡和触发顺序，不应在战斗主流程里增加“如果是焰狐”的特判。

技能代码只获得本场战斗需要的查询和效果能力；活动代码只获得当前活动进度、可信结果和已声明奖励的领取能力。不给内容代码一个可以访问整个系统的万能上下文。

### 5.3 禁止绕过公共规则

活动不得直接修改玩家金币、写入宠物实例、访问其他玩家数据、修改其他活动进度，或接受客户端自报的胜利结果后直接发奖。

活动的服务端规则负责判断自身完成条件；常驻系统负责对象权限、公共结算、事务、额度约束和重复领取保护。基础框架不会自动理解任意玩法，不能把活动正确性全部推给一个通用发奖函数。

随机数、定时任务、事件订阅和资源注册通过受控接口使用，便于复现、限制和清理。内容代码原则上不直接访问文件系统、网络、生产密钥或自行创建无法追踪的长期任务。

### 5.4 常驻系统扩展的申请边界

使用已有能力的内容更新与新增公共机制分开处理。改变行动顺序、持有规则、永久属性、公共存档结构、权限或新增底层结算阶段，必须进入常驻系统变更流程。

每次申请说明：现有能力为什么不够、新能力服务于什么明确需求、影响哪些旧内容、需要什么兼容性测试，以及不做这项扩展的替代方案。

复杂的一次性活动不自动上升为公共框架；全局一致性约束即使暂时只有一个活动使用，也应由常驻系统承担。

## 06｜热插拔与插件生命周期

### 6.1 热插拔分为不同能力

| 能力 | 本方案的首版处理建议 |
| --- | --- |
| 已部署活动在线开放、关闭、重新开放 | 必须落实并测试 |
| 装配不同版本的内容清单、参数与素材 | 校验后切换，保护已有会话的一致性 |
| 新旧插件版本并行服务不同会话 | 架构预留，按实际更新需求实现；不支持时先排空会话 |
| 任意代码在进程内无重启替换并完整卸载 | 不视为天然具备；单独评估与验收 |

已确认的方向是版本内容可热插拔，具体“不停服”范围仍待确认。本稿不把活动启停偷换成任意代码热替换，也不承诺第一版已经实现后者。

### 6.2 基本生命周期

```text
加载并校验 → 已加载未开放 → 开放 → 收尾 → 停用
```

加载阶段验证接口兼容、依赖、素材、数据结构和配置。失败时撤销本次注册，不能留下半加载入口。开放后允许新会话进入；进入收尾后拒绝新会话，但按规则处理已有会话与其合法结算。

停用时注销入口、监听、定时任务、缓存和临时资源。宿主记录注册归属并统一清理，不能只依赖每届设计者记住手工退订。

停用状态需要持久化，服务器重启不能意外重新开放已经关闭的活动。

### 6.3 关闭与强制终止

正常关闭优先采用“禁止新进入、已有会话完成”。强制终止必须事先定义退出、材料返还、奖励和补偿策略，且相关操作可重复调用而不重复生效。

隐藏页面不等于关闭活动，服务端也必须拒绝不再允许的入口请求。另一方面，关闭新入口不应误伤收尾会话已经满足条件的合法结算。

插件存在不能结束的会话或待结算操作时，不能宣称完成卸载。可进入故障隔离或维护状态，保留诊断记录并按既定策略处理。

### 6.4 版本一致性

战斗或活动会话绑定创建时的规则与内容版本，新会话使用新版本。运行中的会话不得突然切换技能含义、奖励表或状态结构。

只有确实保留旧版本代码与资源、且存档可以恢复时，才能支持旧会话继续运行；首版做不到时采用排空会话后维护发布，不伪装成无感热更新。

客户端素材和协议应与会话版本兼容。遇到不支持的版本组合，应停止提交新行动并明确提示刷新或等待，而不是带着错误界面继续操作。

### 6.5 边界不等于安全沙箱

首版运行经过审核、随发布交付的可信插件，不开放用户任意上传代码即时执行。目录约束、类型接口和 Agent 提示词不能被当成完整运行时安全隔离。

同进程中的失控计算仍可能影响整个服务。先控制触发链和计算预算；确需运行难以约束的计算时，再将其放入可独立终止的执行环境，不默认把每个活动都拆成微服务。

## 07｜永久内容、退场与兼容性

### 7.1 活动生命周期与永久内容生命周期分开

```text
火山节活动 → 引用焰狐定义与获宠能力
焰狐定义   → 不依赖火山节正在开放
```

活动负责获得宠物的途径。玩家已经获得的宠物，不能因为活动结束而缺失属性、技能、进化或必要素材。

这不是增加第三个顶层系统，而是内容依赖和保留规则。具体宠物内容由常驻的内容加载能力管理，公共框架不因此出现每只宠物的特判。

### 7.2 发布后必须保留的内容

玩家仍然持有的宠物定义、必要技能实现和资源必须可用。仅保存宠物 ID 或属性快照，不会自动消除技能代码依赖；如技能实现位于待卸载活动模块中，应先解除依赖，否则不能完整卸载该模块。

可以更新内容实现，不要求永远保留所有历史代码。改变含义或结构时必须提供迁移与兼容性验证，且不能复用旧 ID 指向另一只宠物。

### 7.3 活动关闭后的数据策略

上线前必须说明进行中挑战、未领奖励、活动道具、临时货币、兑换入口和进度的退场方式。清理活动临时资源不等于删除永久资产或必要的领取审计记录。

复刻同一活动时，需要明确是继续原进度还是开启新轮次。若新轮次允许重新领奖，必须用明确的轮次标识区分；不能依靠删除领取记录实现“重开”。

### 7.4 控制永久维护负担

活动会退场，但每只永久宠物都可能进入未来的兼容性集合。新宠物优先组合现有机制，对新增公共机制、专属运行逻辑和长期素材体积设定版本预算。

每次迭代同时检查已有内容，不把维护时间全部让给新品。暂不规定固定更新频率或永久宠物数量，先通过前两个版本记录实际设计、测试与维护工作量。

## 08｜Playground：设计者的受限创作环境

### 8.1 运行同一套正式规则

Playground 使用同一套常驻系统、当前插件和独立测试数据，而不是另写一套近似模拟器。允许直接选择宠物、等级和队伍，进入指定活动阶段，固定随机种子，查看结算与生命周期记录。

界面提供可发现的调试入口，不要求设计者输入开发命令或读代码才能完成常见试玩。

### 8.2 三重边界

| 边界 | 要求 |
| --- | --- |
| 修改范围 | 默认只改本活动目录和对应测试；修改常驻系统、公共协议、存档或 CI 需独立流程 |
| 可调用能力 | 只使用声明过的公开接口，不访问生产数据库、其他活动内部或全局服务定位器 |
| 运行环境 | 独立测试存档、无生产密钥、无正式发奖能力；试玩结果不进入玩家正式资产 |

这些限制同时落实在任务说明、导入检查、变更范围检查和实际权限上。Agent 不应能够通过修改自己的检查脚本，取消本次任务约束。

### 8.3 最小调试与导出能力

支持快速重置测试账号、构建指定队伍、重放失败场景、模拟重复请求与断线、执行完整启停过程，以及导出脱敏复现包。

复现包包含必要版本、输入、状态摘要和错误记录，不包含生产密钥、会话令牌或无关玩家资料。

## 09｜推荐技术栈与部署起点

### 9.1 技术选择状态

以下为本次讨论形成的首版推荐组合，不是已经建成或经过容量验证的环境。实施时选择当时受支持的稳定版本，锁定依赖与构建环境，不在本文冻结未经实施验证的软件版本号。

| 部分 | 首选建议 | 边界 |
| --- | --- | --- |
| 语言 | TypeScript | 前后端统一类型与部分规则，不把服务端秘密打入浏览器 |
| 前端构建 | Vite | 开发与构建工具，不作为正式业务服务器 |
| 2D 表现 | Phaser | 场景、动画、相机与输入表现，不持有权威规则 |
| 界面 | React + HTML/CSS | 图鉴、背包、活动、队伍等信息密集界面 |
| 后端 | Node.js 受支持 LTS + Fastify | 账号、指令、存档、活动与管理接口 |
| 数据库 | SQLite 起步 | 单服务、短事务、明确备份与迁移流程 |
| 通信 | HTTP 为主，按需增加 WebSocket | 同场战斗或实时房间确认后再选择房间管理方案 |
| 测试 | 单元测试 + 浏览器端到端测试 + 内容校验 | 可采用 Vitest、Playwright；工具不是验收标准本身 |

若确认使用完整 3D 表现，重新评估客户端渲染栈，而非强行把 Phaser 当 3D 引擎。若多人房间成为核心，可评估 Colyseus，但不同时叠加多个相互重叠的房间框架。

PostgreSQL 可作为直接替代选择，特别是在团队更熟悉它或明确需要多服务进程时；不要求初版同时维护 SQLite 与 PostgreSQL 两套实现。

### 9.2 服务器预算估算

| 档位 | 配置起点 | 适用条件 |
| --- | --- | --- |
| 精简原型 | 1 vCPU / 1GB / 20GB SSD | 资源少、单进程、SQLite，不在该机器上构建或运行复杂预览 |
| 推荐小范围起步 | 2 vCPU / 2GB / 40GB SSD | 目标 5–10 人并发，正式能力仍以压测为准 |
| 较宽裕方案 | 2 vCPU / 4GB / 40–80GB SSD | 同机有额外工具、测试环境或采用更重部署组合 |

以上不是厂商官方最低要求，也不是已验证承载承诺。默认服务器不承担 Agent 推理、GPU 渲染或项目构建；构建交给独立开发或 CI 环境。

逻辑流量可先按 5–10Mbps 出口预算讨论，素材下载单独评估。图片与音频很少时可同机托管，首次加载成为问题后再拆静态托管或 CDN；不为了形式完整提前增加服务。

### 9.3 容量验收与基础安全

在实际候选机器上模拟目标 10 人并发和约 20 人短时峰值，覆盖登录、战斗、抓宠、保存、领奖和重连。记录响应延迟、CPU、内存、数据库等待、错误率和长时间运行趋势。具体数值门槛在原型基线测量后冻结，不预先把估算伪装成 SLA。

测试须区分网络传输与服务器计算，素材加载与指令处理。正式环境只开放必要端口，使用加密传输、身份验证、资源归属检查、管理权限分离和适当的请求频率限制。

开发、预览与正式数据必须隔离。独立数据库并不自动解决同机资源争用，低配正式服务器不应同时承担重构建、压测和大量预览任务。

## 10｜人类与 Agent 的协作机制

### 10.1 人类不编码，但仍拥有产品决策权

人类负责体验目标、规则含义、内容范围、平衡取舍、异常情形下玩家权益，以及是否接受已知风险上线。可以确认设计和试玩结果，不要求逐行审查代码、执行服务器命令或编写测试。

Agent 负责实现、技术方案、测试、排错、文档同步和维护候选修改。自动化流程负责执行验证、产生证据、约束发布，并执行已经批准的有限恢复操作。

人类点击批准不能替代缺失的技术证据。存在无法证明安全的关键数据变更时，默认不发布，先补证据或收缩范围。

### 10.2 从两个 Agent 职责开始

实现 Agent 读取设计，判断是否触及常驻系统，完成修改、测试与说明。独立检查 Agent 从原始设计、实际代码和真实测试结果出发检查，而不是只阅读实现者的总结。

两者可以使用同一模型，但分开任务上下文。独立检查不是正确性证明，两个 Agent 可能共享误解；必须结合运行证据、故障场景和人类试玩。

不为此先造复杂多 Agent 平台。清楚的任务、受控权限、固定验证命令和可复用验收，比增加角色数量更重要。

### 10.3 两条变更路径

| 项目 | 内容迭代 | 常驻系统维护 |
| --- | --- | --- |
| 默认范围 | 当前插件及其测试 | 明确列出的公共能力 |
| 公共存档 | 默认不改 | 提供迁移和兼容验证 |
| 既有公共测试 | 不得随意弱化 | 只有已批准规则变化才可对应调整 |
| 验证范围 | 插件生命周期 + 公共验收 | 所有受影响内容与旧存档 |
| 发布说明 | 玩法变化、活动启停、已知限制 | 公共行为变化、迁移、兼容与恢复限制 |

发现需要常驻系统扩展时，先报告缺口和替代方案，再进入独立任务。不得在制作一个新宠物时隐含进行大规模框架重构。

### 10.4 每次交付的最低内容

交付可试玩版本、实际改动范围、行为变化说明、测试结果与证据、未验证项、存档影响、启停与恢复方式，以及需要人类作出的具体设计决定。

验证结果必须对应实际候选提交和构建产物。不得使用旧报告、未执行的测试、被跳过的关键任务或口头承诺替代本次验证。

## 11｜验证体系与不可破坏的行为约定

### 11.1 验证层次

规则测试验证伤害、状态、成长与结算；内容校验检查引用、数据范围、进化链和素材；集成测试验证数据库、并发与恢复；浏览器端到端测试验证真实客户端行为；人工试玩验证可理解性、节奏与乐趣。

可以增加自动生成操作序列的属性测试，检查库存、领取次数和状态一致性。测试覆盖率是辅助信息，不以单一百分比代替正确性判断。

### 11.2 首批公共验收场景

| 编号 | 场景 | 必须成立的结果 |
| --- | --- | --- |
| C01 | 同一奖励请求连续或并发提交 | 只发放一次，返回一致领取结果 |
| C02 | 两个页面消耗最后一份道具 | 最多一个成功，库存和结果一致 |
| C03 | 捕捉结算中发生异常或进程退出 | 不出现只扣材料、丢结果或重复获宠 |
| C04 | 战斗断线后重连 | 恢复已确认状态，不能重抽随机结果 |
| C05 | 请求携带他人宠物或会话 ID | 服务端拒绝越权操作 |
| C06 | 使用过期状态提交行动 | 拒绝冲突操作并提供同步方式 |
| C07 | 活动进入收尾 | 拒绝新会话，已有会话按规则结算 |
| C08 | 加载失败或重复启停 | 无半注册入口、重复监听和残留任务 |
| C09 | 停用活动后重启服务器 | 不意外重新开放，不重置领取记录 |
| C10 | 活动退场后使用已获得宠物 | 属性、技能、进化与必要表现仍正常 |
| C11 | 新版本加载代表性旧存档 | 持有关系、背包和关键进度正确 |
| C12 | 复刻活动并开启新轮次 | 领取按轮次规则执行，不误发旧轮次奖励 |
| C13 | 极端触发链与大量状态叠加 | 正确终止或受控拒绝，不无限执行 |
| C14 | 关闭一个插件后操作其他系统 | 其他活动、账号与常驻循环不被破坏 |
| C15 | 在隔离环境恢复备份 | 可启动、登录，并核验宠物、背包与领取记录 |

公共规则的设计含义由人类确认，代码测试由 Agent 实现。合理的规则修改允许更新测试，但必须明确说明旧约定为什么改变，不能单纯为让 CI 通过而改断言。

### 11.3 回归与证据

每个真实缺陷尽量形成可复现场景，验证修复前失败、修复后通过。保存代表性旧存档、固定随机场景与插件启停用例，供后续版本复用。

浏览器证据结合操作记录、截图或录像、网络与服务端结果。Canvas 画面不能仅凭 DOM 存在就判定正确；服务端发奖正确也不能替代人类对表现和玩法的验收。

必要检查应汇总确认全部实际执行，不把被跳过的关键任务当作成功。缺少证据的项目标记为未验证，不写成已经完成。

## 12｜发布、权限与变更控制

### 12.1 发布流程

```text
确认设计 → 实现 → 自动验证 → 独立检查 → 隔离试玩
         → 固定候选构建 → 人类确认产品结果
         → 受控部署 → 暂不开放 → 检查 → 开放活动
```

发布使用已验证的固定构建产物，记录提交、依赖、内容清单、数据版本和开放配置。禁止测试一个提交、上线另一个提交，或在正式机器上临时安装不受控的新依赖。

对无法在线安全替换的代码变更，先收尾会话并进入短维护。热插拔负责独立装配和开放控制，不负责绕过发布验证。

### 12.2 权限原则

普通内容 Agent 默认无生产数据库、服务器管理员、备份删除和仓库安全规则修改权限。实现 Agent 提交候选变更，不直接自行合并、部署并开放生产内容。

公共测试、发布脚本和关键权限策略受独立保护；相关维护不能与普通内容任务混在一起。生产操作通过受限的发布与运营入口执行，凭据不进入聊天、代码、构建日志或复现包。

管理账号可以配置规则与审批产品取舍，这不要求人类写代码。初始化的外部账号授权和密钥托管仍须明确负责人，不能假定 Agent 会自动取得权限。

### 12.3 迁移与退回

公共数据变更先在代表性旧存档上验证，再验证迁移失败和再次执行的行为。发布前创建可恢复备份；破坏性删除优先延后，不与新内容开放捆绑。

代码退回上一版要求旧代码兼容当前数据，不得默认顺带回退玩家进度。数据库恢复是另一项操作，可能丢失备份之后的有效变化，必须明确影响和授权。

错误发奖优先依据领取和资产记录定位后修正或补偿，不默认回滚整个服务器。不可自动决定的大规模玩家权益变更交给人类作产品决策。

## 13｜运行观测、故障处理与数据恢复

### 13.1 最小运营面板

提供当前应用与插件版本、活动开放状态、在线会话、近期错误、备份结果和基础资源使用情况。允许受控地关闭活动入口、暂停指定领取、进入维护和查看复现标识。

不必初期搭建庞大监控平台。先保证出了问题能知道哪个版本、哪个活动、哪个请求发生了什么，以及影响哪些玩家资产。

日志至少关联玩家内部标识、请求、战斗或活动会话、插件与版本；不得明文记录密码或会话密钥。容量、保留周期与告警渠道在上线前确认。

### 13.2 故障处理流程

```text
发现异常 → 预定止损 → 保留记录 → 隔离环境复现
         → 补回归测试 → 修复 → 重新验证与受控发布
```

自动止损限定在已经批准、可审计的动作，例如阻止新建异常活动会话。原则上不让 Agent 在正式服反复试补丁，也不允许其自主清档、批量回收资产或任意补偿。

插件错误无法局部恢复时，可以进入整体维护。相比无证据地保持在线，保护数据与确认状态优先。

### 13.3 备份与恢复

建议至少每日异机备份，并在重要发布和数据迁移前额外备份。备份需访问隔离、合理保留周期，并考虑玩家数据的敏感性。

定期在隔离环境实际恢复，验证应用启动、登录、持有宠物、背包和领取记录。备份文件存在或任务成功，不能单独证明可恢复。

可将“最多损失 24 小时数据、恢复目标 2 小时”作为首轮讨论用目标；这不是现有能力，也不自动适合玩家需求。正式留档前由人类确认可接受范围，并用演练验证；不满足就调整备份频率、恢复方式或运营承诺。

### 13.4 维护事项

定期检查依赖与安全更新、磁盘与日志增长、数据库与备份、旧内容兼容性和长期未解决问题。一般依赖升级独立于活动发布，紧急风险不等待常规版本周期。

至少记录异常能否复现、修复是否附带回归测试、恢复演练是否成功，以及新内容是否频繁要求修改常驻系统。它们比代码行数更能反映维护健康度。

## 14｜持续共创与内容运营

### 14.1 人员可以更换，规则与证据必须持续

设计者轮换不等于每届重新解释公共规则。项目保留固定的设计决策入口和常驻系统维护流程，执行这些流程的 Agent 可以更换。

新设计者应能通过玩法说明、创作范围、公开能力和一个完整示例，完成新内容。不能以“先完整阅读整个仓库”作为正常创作前提。

### 14.2 长期知识留在仓库

| 材料 | 维护要求 |
| --- | --- |
| 设计与行为约定 | 人类确认规则含义，Agent 同步文档；与临时设想分开 |
| 架构、公开接口与示例 | 描述当前真实实现，不堆积过期方案 |
| 验证、发布与恢复流程 | 命令和步骤可执行，随实现更新并经过演练 |

根目录 AGENTS.md 保留最重要的全局约束；活动目录补充本活动需求与范围，不重复整套文档。临时计划和推测不得覆盖已确认设计。

### 14.3 更新节奏与复杂度预算

每个版本为内容设计、测试、兼容、依赖维护和问题修复保留容量。新公共机制的数量需要控制，但不在未经历实际版本前承诺固定周更、月更或宠物产量。

活动可以复刻、轮换或延后；基础循环始终可玩。商业化、付费和公开发行未在讨论中确定，本稿不假设它们存在。

新增素材应具有可追溯来源与使用依据。玩法参考不等于使用参考游戏的角色、美术、音频或文字；人类负责创作方向与内容审核，Agent 不擅自挪用外部素材。

### 14.4 可持续性的实测指标

新活动需要修改多少公共代码？交接给新 Agent 是否需要大量口头背景？关闭旧活动是否要临时写脚本？永久宠物是否仍然可用？错误是否有足够记录复现？备份能否真正恢复？

这些问题定期用实际操作回答，而不是仅检查文档数量或测试覆盖率。

## 15｜实施路线与阶段验收

### M0｜冻结第一轮设计边界

确认多人交互模式、二维或三维表现、队伍人数、最小战斗规则、抓宠与成长行为、首个活动范围，以及热插拔的首版验收含义。

产出设计基线、首批公共行为约定和首个活动设计。不进入万能插件系统建设。人类确认规则，Agent 整理可实施规格与缺口。

### M1｜完成常驻端到端流程

实现登录、最小队伍、一次完整战斗与捕捉、升级或进化、保存并重新进入。至少以两个真实客户端验证隔离、并发和重连。

验收要求：服务端裁决、关键事务一致、请求可安全重试、断线不会重抽结果。若合作战斗被确认为核心，必须在本阶段验证同场协作。

### M2｜完成第一个活动插件

制作一个包含进入、进度、挑战、获宠与退场规则的完整活动。交付 Playground、插件元信息、公开能力和生命周期测试。

验收要求：不直接写公共资产，活动可关闭、收尾和重开，无重复监听或奖励；活动关闭后已获得宠物继续正常使用。

### M3｜进行共创与交接验证

由第二位设计者和一个未参与原实现的 Agent，依据仓库材料制作第二个活动；同时停用第一个活动并验证永久内容。

记录需要解释的背景、公共框架改动和接口缺口。只抽取已经出现的稳定需求，不为了未来可能性再次全面重构。

验收要求：不依赖旧对话，能通过公开能力完成内容；旧内容退场不破坏账号、常驻循环和已获得资产。

### M4｜完成运营演练并开放长期留档

完成固定构建与受控发布、候选机器压测、异机备份与恢复、错误复现、活动止损和维护流程演练。

验收要求：关键公共测试实际执行，通过代表性旧存档验证；运营入口可用；恢复目标经过确认与演练；不存在未解决的重大资产一致性问题。

先开放约 10–20 人的小范围长期留档，不把尚未验证的吞吐或无感热更新对外承诺为既有能力。

## 16｜上线门槛、风险与待定事项

### 16.1 长期留档前的门槛

公共资产操作经过重复请求与并发测试；授权和归属检查通过；断线与重启可恢复；活动启停与收尾可验证；永久内容不依赖退场活动；发布绑定实际测试产物；有受控维护入口；异机备份恢复成功；人类明确知道仍未验证的范围。

缺少重大技术证据时不发布，不把是否上线转化为人类对未知实现的盲目确认。

### 16.2 主要风险与应对

| 风险 | 应对方向 |
| --- | --- |
| Agent 为实现内容频繁重构框架 | 修改范围限制、公共扩展独立任务、要求现实需求依据 |
| 验证由同一 Agent 自我证明 | 公共测试保护、独立检查、真实执行证据与人工试玩 |
| 任意玩法使框架失去边界 | 明确能力清单、机制预算、超范围先设计评审 |
| 活动下线破坏永久宠物 | 单向依赖、长期内容保留、存档引用检查与退场测试 |
| 热更新破坏进行中会话 | 版本绑定，保留依赖；不能安全共存时排空后维护 |
| 错误结算污染正式资产 | 服务端权威、事务、持久去重、审计与受控止损 |
| 备份存在但恢复失败 | 隔离恢复演练与真实业务核验 |
| 依赖旧会话和单个 Agent | 仓库基线、示例、可执行流程与换 Agent 接手实验 |
| 内容积累超过维护能力 | 保持常驻循环，限制新机制，安排维护而非只加内容 |

### 16.3 开始实现前仍需确认

| 决策 | 当前状态 | 必须确认的时点 |
| --- | --- | --- |
| 多人形式：独立冒险、合作同场或其他 | 未定 | M0，影响第一条可玩流程 |
| 美术与渲染：2D 或 3D | 建议 2D，未定 | M0，影响客户端与素材规格 |
| 队伍人数与行动顺序 | 建议先小队，具体未定 | M0，影响规则与界面 |
| 捕捉、失败、进化与奖励细节 | 未定 | M0，先覆盖首个完整流程 |
| 热插拔是否要求任意代码完全不停服 | 目标已提出，具体范围未定 | M0 定首版，后续能力单独验收 |
| 设备范围与移动端优先级 | 未定 | 界面和输入设计前 |
| 账号进入方式与管理员权限 | 未定，建议小范围受邀进入 | 正式联网测试前 |
| 活动周期、复刻和未领奖励处理 | 未定 | 每个活动上线前 |
| 可接受数据损失与恢复目标 | 未定 | 长期留档前 |
| 商业化与公开发行 | 未提出，不作默认假设 | 如未来进入范围，另行设计 |

待定项不要求一次讨论完所有远期细节。以阻碍当前阶段的决策为优先，其余保留为明确待办，不由 Agent 静默补全。

## 附录 A｜首个活动设计交付模板

**活动名称与目标体验：** 玩家会经历什么，核心乐趣是什么。  
**进入与结束条件：** 谁可以进入，何时关闭，已有会话如何收尾。  
**主要流程：** 从进入、进度推进、挑战到退出的可观察步骤。  
**宠物与奖励：** 获得途径、领取次数、消耗、永久内容依赖。  
**失败与异常：** 失败、断线、重复操作、强制关闭的预期行为。  
**需要的公共能力：** 已有能力与缺口分别列出。  
**活动专属数据：** 记录哪些进度，复刻时是否重置，如何区分轮次。  
**表现与素材：** 页面、角色、技能表现、规格和来源要求。  
**验收场景：** 正常流程与异常流程的具体输入、操作和预期结果。  
**退场策略：** 未领奖励、临时货币、道具、记录与永久宠物如何处理。  
**不在本次范围：** 明确不实现的机制，防止任务被自动扩大。

模板由人类填写设计意图，Agent 可以提出缺失问题和实施建议，不把技术细节反向强加为未经确认的玩法。

## 附录 B｜Agent 全局工作约束建议

1. 开始实现前读取当前设计基线、公开接口与本任务范围；标记未确认的产品决定。
2. 普通内容任务只修改本插件和对应测试；公共规则、存档、权限与 CI 变更进入独立流程。
3. 不在公共战斗流程里新增具体宠物或活动的身份特判。
4. 不绕过公共资产结算，不采信客户端提交的最终奖励或胜负结果。
5. 不为一次性内容强行设计通用系统；新增结构说明对应的当前需求。
6. 不删除、跳过或弱化既有公共测试来获得通过状态。
7. 修复缺陷时尽量先提供能复现的失败用例，再验证修复后通过。
8. 不使用生产数据与密钥进行普通开发，不自行访问或修补正式服务器。
9. 文档、接口示例和测试随实际实现同步；未验证内容明确标注。
10. 交付提供真实测试证据、可试玩版本、已知限制和安全停用方式。
11. 发现需要人类决定的玩法或玩家资产处置时提出具体选项，不静默代替决策。
12. 缺少关键发布证据时停止发布，不以另一位 Agent 的口头同意代替验证。

这些约束需要配合实际仓库、运行与发布权限，不仅是一份提示词。

## 附录 C｜候选版本验收报告模板

**版本与构建：** 提交标识、内容清单、插件版本、数据版本。  
**玩家可见变化：** 新增、修改与移除的行为。  
**改动边界：** 是否修改常驻系统、协议、公共存档或权限。  
**验证结果：** 实际执行项目、通过与失败、证据位置、未执行项目及原因。  
**兼容性：** 哪些旧存档、旧宠物与活动经过验证，哪些未覆盖。  
**生命周期：** 开放、收尾、停用、重开和重启的验证结果。  
**资产与恢复：** 迁移影响、备份、代码退回限制、恢复策略。  
**已知问题：** 玩家影响、风险范围、临时规避方式。  
**设计待决：** 需要人类确认的具体产品决定。  
**发布结论：** 可进入试玩、可发布、或阻止发布，并列出依据。

## 结语｜项目最终应积累什么

项目的长期资产不仅是宠物、活动和代码，还包括明确的行为约定、稳定的公开能力、可运行的验证、真实发布记录和经过演练的恢复流程。

**目标不是让某个 Agent 永远记住并维护整个项目，而是让新的设计者和新的 Agent 都能理解、验证、接手与继续推进它。人类可以不编码，但项目不能没有明确规则、可信证据和受控的技术执行。**
